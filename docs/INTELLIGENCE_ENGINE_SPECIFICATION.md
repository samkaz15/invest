## 1. 設計思想と分析パイプライン

### 1.1 このエンジンは何であって、何でないか

BIOSは**価格予想AIではない**。事実を構造化し、因果を解析し、過去事例と比較し、複数シナリオを確率で評価し、意思決定を支援する**分析OS**である（憲法第1条）。したがって本書のすべてのエンジンは次の3つを守る：

1. **出力は常に「構造＋確率＋無効化条件」**。断定予想はスキーマに存在しない。
2. **すべての数値はDB由来**。LLMは解釈と構造化を担い、数値の生成はしない。
3. **すべての主張はラベル（FACT/REPORTED/INFERENCE）と証拠を持つ**。

### 1.2 分析パイプライン（10段階・厳守）

憲法第2条の順序をエンジン構成にそのまま写像する。**下流は上流の成果物のみを入力にできる**（飛ばし・逆転は構造的に不可能にする）。

| 段階 | 内容 | 担当エンジン/Agent | 成果物 |
|---|---|---|---|
| 1. Fact | 何が起きたか（検証可能な一次情報のみ） | News/On-chain/Derivatives/Macro Agent（G1-G5） | Event＋summary_fact |
| 2. Evidence | 出典・引用・取得日時・信頼度 | 同上＋QA Agent | Evidence（tier・quote・retrieved_at） |
| 3. Timeline | いつ起きたか・前後関係 | Timeline Engine（MSD §9） | 時系列整列・Chain進行 |
| 4. Context | どういう状況下か | Market Phase判定（§10） | Regime＋Phaseタグ |
| 5. Cause | Trigger（発端）とBackground（背景）の分離 | Analysis Engine（§2） | 因果エッジ（証拠つき） |
| 6. Market Reaction | 市場は実際にどう動いたか | Reaction焼付バッチ（MSD §11） | market_reactions |
| 7. Historical Comparison | 類似事例・基準率・今回との差分 | Similarity Engine（§9） | historical_matches＋base_rate |
| 8. Scenario Analysis | 複数シナリオの構築 | Scenario Agent（G12） | scenario候補 |
| 9. Probability | シナリオ別確率（基準率起点＋調整明記） | Scenario Agent＋Scoring Engine | scenario_set（Σp=1.0） |
| 10. Decision | BUY/WAIT/TAKE_PROFIT＋無効化条件 | Risk Agent（G13）＋Critic（G16） | decision（Journal） |

**段階間の契約**：各段階の出力はPydanticスキーマで検証され、検証を通らない成果物は下流に渡らない。段階Nの成果物には段階N-1の成果物IDへの参照を必須とし、監査時に任意のDecisionから段階1まで完全遡及できる（証拠チェーン）。

### 1.3 テーマ別エンジンの共通インターフェース

§3〜§8の各エンジン（Supply/Demand/On-chain/Derivatives/Macro/Anomaly）は、同一の出力契約を持つ**Dimension Analyzer**として設計する。これによりScoring Engine（§11）が統一的に統合できる。

```jsonc
// DimensionReport（全テーマ別エンジン共通の出力契約・毎日1件/次元）
{
  "dimension": "supply",            // supply | demand | onchain | derivatives | macro | anomaly | news
  "as_of": "2026-07-14T05:00:00Z",
  "asset_id": "ent_asset_btc",
  "score": -35,                     // -100（最弱気）〜 +100（最強気）
  "conviction": 0.7,                // この次元の分析自体の確度 0-1
  "signals": [                      // スコアの内訳（説明可能性の単位・§11.2）
    { "signal_id": "supply.overhang_ratio", "value": 3.2, "unit": "days_of_absorption",
      "points": -20, "label": "INFERENCE",
      "rationale": "既知供給圧が日次吸収能力の3.2日分",
      "evidence_refs": ["evt_...", "snapshot_..."] }
  ],
  "key_findings": ["..."],          // 人間可読の要点（Report Agent向け・最大5行）
  "watch_items": ["..."],           // この次元のnext_watch
  "data_gaps": ["..."],             // 欠損データの明示（沈黙の欠損禁止）
  "invalidation": "..."             // この次元評価が崩れる条件
}
```

## 2. News Intelligence Engine

### 2.1 責務

ニュースを「要約」ではなく**14項目の構造化分析**へ変換する。対象はキュレーション済みの正規Event（ニュース由来）であり、生記事の直接分析はしない（Event First原則。1出来事=1Event＋N Evidence）。

### 2.2 処理フロー

```
正規Event（news系） → Scoring Agentが分析深度を選別
  ├─ magnitude ≥ 3 → 完全分析（14項目・上位モデル）
  ├─ magnitude 2   → 簡易分析（Fact/解釈/スタンスのみ・軽量モデル）
  └─ magnitude 1   → 分析なし（Event記録のみ）
完全分析 = Similarity Engine（§9）＋因果分析＋反応分析の統合として生成
```

### 2.3 出力スキーマ（news_analysis v2 — 14項目）

MASTER_SYSTEM_DESIGN §12.1 の13項目に **Potential Future Impact** と **Action Items** を追加した後方互換拡張（フィールド追加のみ）。

```jsonc
{
  "event_id": "evt_...", "analyzed_at": "...", "agent_versions": {...},

  "fact": "...",                        // 1. 何が起きたか（FACTのみ・証拠ID必須）
  "why": "...",                         // 2. なぜ起きたか
  "trigger": "...",                     // 3. 発端（直接のきっかけ）
  "background": "...",                  // 4. 背景（構造的要因）
  "timeline": [{"ts": "...", "desc": "...", "evidence_id": "..."}],  // 5. 時系列
  "market_interpretation": "...",       // 6. 市場はどう解釈したか（実反応データと突合）
  "historical_matches": [...],          // 7. 類似事例（§9出力。相違点・confounding必須）
  "current_status": "...",              // 8. 現在の状況（Chain進行状況と連動）
  "potential_future_impact": {          // 9. 今後の影響（★v2追加）
    "paths": [ { "path": "返済BTCの30%が市場売却される場合", "impact": "...",
                 "probability_hint": "base_rate参照", "horizon": "+30d" } ],
    "label": "INFERENCE"                //    影響予測は必ずINFERENCE
  },
  "stance": "bearish",                  // 10. bullish | bearish | neutral
  "confidence": 0.65,                   // 11. 0-1（キャリブレーション対象）
  "next_watch": ["..."],                // 12. 次に監視すべき事象
  "invalidation": "...",                // 13. この分析が崩れる条件
  "action_items": [                     // 14. トレーダーが次に確認すべきこと（★v2追加）
    { "action": "Krakenへの入金アドレス群の残高を確認", "when": "daily",
      "source": "on-chain", "auto_trackable": true }   // auto_trackable=trueはwatch_pointsへ自動登録
  ],
  "claims_audit": {...}                 // QA検査結果
}
```

### 2.4 規律

- **全ニュース分析は一次情報・引用元・取得日時・信頼Tierを持つEvidenceに紐づく**（Evidenceのないニュース分析はスキーマ違反）。
- `market_interpretation`は「市場はこう解釈したはず」ではなく、**実際の反応データ（価格・フロー・デリバ）と突合**して書く。反応と解釈が食い違う場合（好材料に無反応等）はそれ自体を`key_findings`に昇格させる（織り込み済みシグナル）。
- `action_items`のうち機械追跡可能なもの（`auto_trackable: true`）はTimeline Engineの`watch_points`へ自動登録し、翌日以降の日次チェック対象にする。

## 3. Supply Shock Engine

### 3.1 責務

市場へBTCが供給される（売り圧になる）イベントを分類・定量化し、**「今後N日で市場に出得る量」と「市場の日次吸収能力」の比較**として供給圧を評価する。実行主体はSupply Shock Agent（G8）。

### 3.2 供給源の分類（Supply Taxonomy）

| 分類 | 例 | 特性 |
|---|---|---|
| 破産財団分配 | Mt.Gox, FTX, Genesis, BlockFi, Celsius, Voyager, 3AC | 規模大・スケジュール既知・受領者の売却率が不確実 |
| 政府売却 | 米政府（押収）, 独政府 | 規模既知（ウォレット追跡可）・裁量的・アナウンス効果大 |
| 企業売却 | Tesla売却等 | 開示で発覚（事後）・裁量的 |
| ETF流出 | GBTC流出等 | 日次観測可能・持続性が焦点 |
| Exchange Inflow | 大口の取引所入金 | 売り意図の先行指標（ただし入金≠売却） |
| Whale Sell | 大口保有者の分売 | オンチェーン推定・帰属確度に依存 |
| Miner Selling | マイナー準備金取崩し | ハッシュプライス連動・降伏局面で加速 |
| スケジュール供給 | 新規発行（半減期で変化）, ロックアップ解除 | 完全予測可能 |

### 3.3 中核構造：Supply Overhang Ledger（供給圧台帳）

既知の供給圧を1件1レコードで台帳管理する。**これが供給分析の一次資産**であり、日次で更新される。

```jsonc
{
  "overhang_id": "ovh_mtgox_2024",
  "source_type": "estate_distribution",       // §3.2の分類
  "entity_id": "ent_mtgox_estate",
  "chain_id": "chain_mtgox",
  "total_btc": 141686,                         // 総量（FACT・オンチェーン/裁判所文書由来）
  "remaining_btc": 46164,                      // 残量（日次更新・ウォレット追跡）
  "schedule": { "type": "window", "start": "2024-07", "deadline": "2025-10-31" },
  "seller_discretion": "recipient",            // forced(強制) | discretionary(裁量) | recipient(受領者次第)
  "expected_sell_ratio": { "estimate": 0.35, "range": [0.2, 0.6],
    "basis": "類似分配事例の実売却率", "label": "INFERENCE" },
  "venue": "exchange_and_otc",                 // exchange | otc | mixed（OTCは板圧にならない）
  "status": "active",                          // pending | active | exhausted | cancelled
  "confidence": 0.9
}
```

### 3.4 供給圧の定量評価

| 指標 | 定義 | 用途 |
|---|---|---|
| **想定放出量（Expected Flow）** | Σ active台帳の（残量×期待売却率×期間按分） | 今後7/30/90日の売り圧推定 |
| **日次吸収能力（Absorption Capacity）** | 現物実出来高＋ETF純流入＋（OTC推定） の移動平均 | 分母 |
| **Overhang Ratio** | 想定放出量 ÷ 日次吸収能力（単位：日） | 主力シグナル。「吸収に何日分か」 |
| **実現率トラッキング** | 実際のオンチェーン移動・売却 vs 想定 | 台帳の期待売却率を実績で更新 |
| **アナウンス効果分離** | 発表時の反応と実売り時の反応を別Eventで記録 | 「売る前に織り込む」パターンの検出 |

### 3.5 分析規律

1. **「移動」と「売却」を混同しない**。ウォレット移動はFACT、売却はオンチェーン痕跡（取引所入金→残高減）またはエンティティ開示があるまでINFERENCE。
2. **OTC売却は板圧にならない**（独政府の教訓の逆：独政府は取引所直行で影響大、米政府の一部はOTCで影響小）。venueの区別を必ず保持。
3. 過去類似事例・統計はSimilarity Engine（§9）とPattern台帳（MSD §10.3）経由で取得し、**n<5なら統計でなく事例列挙**として扱う。
4. スコア化：Overhang Ratio・ETF流出連続日数・Exchange Inflow z-score・Miner Position変化を`signals[]`としてDimensionReportに集約（§1.3）。

## 4. Demand Shock Engine

### 4.1 責務

需要増加イベントを分類・定量化し、**需要の「規模」だけでなく「継続性（stickiness）」を評価**する。実行主体はDemand Shock Agent（G9）。供給側と対称の設計とし、両者の差引きが需給バランス評価になる。

### 4.2 需要源の分類と継続性特性

| 分類 | 例 | 継続性の仮説（基準率で検証） |
|---|---|---|
| ETF流入 | IBIT等への純流入 | 中〜高。ただしモメンタム追随分は反転しやすい |
| 企業購入 | MicroStrategy型（継続購入プログラム） | 高（プログラム型）／低（一回性） |
| 国家購入 | エルサルバドル, 戦略準備構想 | 高（政策変更まで売らない）・シグナル効果大 |
| Whale Buy | 大口アドレスの蓄積 | 中。蓄積アドレスの過去行動で個別評価 |
| Exchange Outflow | 取引所からの引出し（自己保管） | 高（売却動線から外れる） |
| 長期保有者増加 | LTH供給増・休眠コイン化 | 高。ただし遅行指標 |

### 4.3 定量評価

| 指標 | 定義 |
|---|---|
| **需要フロー** | ETF純流入＋開示済み企業/国家購入＋オンチェーン蓄積推定（7/30日移動平均） |
| **Stickiness Score** | 需要源ごとの継続性0-1（分類基準率×当該主体の過去行動） |
| **粘着需要比率** | Stickiness加重需要 ÷ 総需要（「逃げない金」の割合） |
| **流入半減期** | 過去の類似流入波の減衰半減期（波の寿命推定） |
| **需給バランス** | 需要フロー −（§3想定放出量＋新規発行）。日次で符号と傾きを記録 |

### 4.4 分析規律

1. 需要の**鏡像規律**：引出し（outflow）は「買い」ではなく「売却動線からの退出」。買いはフロー、outflowは在庫の質の変化として別々に扱う。
2. **飽和の検出**：同種需要の連続（企業購入N社目）は限界効果が逓減する。同一パターンの反応の減衰をSimilarity Engineの時系列比較で監視。
3. 過去比較：「ETF流入×レジーム」等のパターン基準率で今回の波の寿命・規模を推定し、調整理由を明記。

## 5. On-chain Intelligence

### 5.1 責務

オンチェーン指標を**単発でなく組み合わせと歴史文脈（percentile/z-score）で解釈**する。実行主体はOn-chain Agent（G3・データ化）＋Scoring Agent（G11・シグナル化）。

### 5.2 指標カタログ

各指標は `config/` のシグナル定義YAMLで管理し、**意味・強気/弱気条件は設定として宣言**する（コード変更なしで閾値調整可能）。閾値は固定値でなく**歴史percentile**で定義する（非定常性対策）。

| 指標 | 意味 | 市場への含意 | 強気条件（例） | 弱気条件（例） | 主な組み合わせ |
|---|---|---|---|---|---|
| **MVRV** | 時価総額÷実現時価総額。市場全体の含み損益倍率 | 過熱/割安の温度計 | <1.0（歴史的底値圏）から回復 | >P90（過熱圏）＋上昇鈍化 | SOPR・LTH-MVRVと併読で世代別過熱を分離 |
| **SOPR** | 使用されたコインの売却損益比 | 1.0が損益分岐。利確/損切り行動の観測 | 調整中にSOPR≈1で反発（押し目買い） | 1.0を下抜け定着（損切り容認） | MVRVと併読：高MVRV＋SOPR低下＝分配開始 |
| **CDD** | Coin Days Destroyed。古いコインの移動量 | 長期保有者の動き検知 | 低位安定（古い手が動かない） | スパイク（古い手の分配）＋価格高値圏 | Dormancyと同方向確認。取引所入金と重なれば売り圧FACT寄り |
| **Dormancy** | 移動コインの平均休眠期間 | 動いたコインの「年齢」 | 低下トレンド（若いコイン中心の回転） | 高値圏での上昇（古い手の出口） | CDD・Exchange Inflowとの三点照合 |
| **Exchange Reserve** | 取引所保有残高 | 即売可能在庫の総量 | 継続減少（自己保管化） | 急増（売り待機在庫の積上げ） | 需給バランス（§4）の在庫側入力 |
| **Whale Activity** | 大口アドレス群の残高変化・送金 | スマートマネーの方向 | 蓄積（残高増＋outflow） | 分配（取引所inflow増） | 帰属confidence必須。§3/§4のフロー入力 |
| **Miner Reserve** | マイナー保有残高 | 構造的売り手の在庫 | 保有増（売り圧低下） | 急減（降伏売り） | Hash Rate低下と同時なら降伏パターン該当 |
| **Realized Price** | 全コインの平均取得単価 | 市場全体の損益分岐線 | 価格がRP上で押し目形成 | 価格がRPを下抜け | LTH/STH別Realized Priceで支持帯を層別 |
| **Hash Rate** | 全網計算力 | マイナーの設備投資健全性 | 最高値更新（長期信認） | 急落（降伏・地政学ショック） | Difficulty調整と併読。短期ノイズ大：14d MAで見る |
| **Difficulty** | 採掘難易度 | Hash Rateの確定値（遅行） | 連続上方調整 | 連続下方調整（降伏確認） | Miner Reserve減と併読で降伏の確度上げ |
| **Stablecoin Supply** | 主要ステーブル時価総額・取引所残高 | 待機購買力（dry powder） | 拡大＋取引所流入 | 縮小（資金退出）・デペッグ | Macroの流動性（§7）と整合確認 |

### 5.3 統合規律

1. **単一指標での結論を禁止**。シグナルは最低2指標の合流（confluence）で1シグナルとする（上表「組み合わせ」列が公認の合流パターン。合流定義もYAML管理）。
2. **すべてz-score/percentile化**（対全歴史＋対同レジーム歴史の2系列）してからスコアに入れる。生値の閾値ハードコード禁止。
3. **遅行性の明示**：オンチェーンは日〜週の遅い信号。日次の方向判断への重みはデリバ・フローより低く設定し、レジーム判定（§10）への重みを高くする。
4. **改訂リスク**：オンチェーン集計値（特にエンティティ帰属系）は事後改訂される。取得時点値を`known_at`つきで保存し、バックテストでは取得時点値のみ使用（point-in-time原則・§13.6）。

## 6. Derivatives Intelligence

### 6.1 責務

デリバティブ市場からポジショニングの偏り・レバレッジの脆弱性・ボラティリティ構造を読み取る。実行主体はDerivatives Agent（G4・データ化＋ルール検知）＋Scoring Agent（シグナル統合）。

### 6.2 監視対象と解釈

| 対象 | 観測値 | 解釈ルール（例） |
|---|---|---|
| **Funding Rate** | Perp資金調達率（主要取引所加重） | 極端な正（>P95）＝ロング過密→スクイーズ脆弱性。極端な負＝ショート過密→踏み上げ燃料 |
| **Open Interest** | 建玉総額・変化率・価格比 | OI急増＋価格横ばい＝ポジション積上がり（エネルギー充填）。OI急減＝清算/手仕舞い完了 |
| **Liquidation** | 清算額・清算クラスタ（価格帯別の清算予想密度） | 清算クラスタは価格の磁石/加速帯。カスケード後はレバレッジリセット（底の条件の一つ） |
| **Options** | IV（期間別）・25d Skew・Put/Call・満期OI分布 | Skewのプット偏重＝下方ヘッジ需要。IV低位＝油断（ショック増幅余地） |
| **Gamma** | ディーラー推定ガンマ（Max Pain・ガンマフリップ点） | 正ガンマ帯＝価格吸着（レンジ化）。負ガンマ帯＝変動増幅。満期直前に影響最大 |
| **Basis** | 先物ベーシス（CME/Perp別・年率換算） | CMEベーシス拡大＝機関のロング需要。逆ザヤ＝極端な悲観（歴史的に底圏で出現） |
| **Long/Short Ratio** | 口座比率・建玉比率 | 逆張り指標として扱う（極端値のみ有効）。取引所間の食い違いは信頼度を下げる |

### 6.3 統合ルール（公認の合流パターン）

単発値でなく**状態の組み合わせ**を検知する。パターンはYAML定義（追加自由）：

| パターン名 | 条件（概略） | 含意 |
|---|---|---|
| `crowded_long` | Funding>P95 ＋ OI高位 ＋ 価格上昇鈍化 | ロング過密。下方清算カスケードの脆弱性 → 弱気シグナル |
| `short_squeeze_setup` | Funding<P5 ＋ OI高位 ＋ 価格下げ止まり | 踏み上げ燃料充填 → 強気シグナル |
| `leverage_reset` | 大規模清算直後 ＋ OI急減 ＋ Funding中立化 | レバレッジ浄化。底形成の必要条件（十分条件ではない） |
| `complacency` | IV<P10 ＋ Skew中立 ＋ OI高位 | 油断。ショック時の増幅余地大 → ボラ買い局面/リスク警告 |
| `institutional_bid` | CMEベーシス拡大 ＋ ETF流入 ＋ Funding正常 | 現物主導の健全な上昇（レバ主導と区別） |
| `gamma_pin` | 大満期接近 ＋ Max Pain近傍 ＋ 正ガンマ | 満期までレンジ吸着。満期通過後に方向解放 |

### 6.4 規律

- デリバシグナルは**時間軸が短い（日〜週）**。日次判断への重みは高く、レジーム判定への重みは低く。
- 清算予想クラスタは推定値（INFERENCE）。実清算額（FACT）と区別。
- 取引所別データの品質差を`data_gaps`で明示（欠損取引所があれば加重を再正規化）。

## 7. Macro Intelligence

### 7.1 責務

マクロ環境をBTCへの**波及経路（transmission channel）単位**で構造化する。「CPIが出た」ではなく「CPI→実質金利期待→ドル流動性→リスク資産→BTC」の経路で分析する。実行主体はMacro Agent（G2）。

### 7.2 監視対象

| 対象 | 観測値 | 主な波及経路 |
|---|---|---|
| FOMC | 政策金利・ドット・声明文差分・議事要旨 | 経路①②（下記） |
| CPI / PPI | 前月比・前年比・コア・予想乖離 | 経路①（利下げ/利上げ期待の更新） |
| NFP（雇用統計） | 雇用者数・失業率・賃金・予想乖離 | 経路①③ |
| GDP / PMI | 成長率・景況感（製造/サービス） | 経路③（景気→リスク選好） |
| DXY | ドル指数 | 経路②（ドル高＝世界流動性引締め） |
| US10Y | 名目・実質（TIPS）金利 | 経路①（実質金利はBTCの機会費用） |
| M2 / Liquidity | M2・Fedバランスシート・RRP・TGA（純流動性） | 経路②（BIOSが最重視する経路） |
| Geopolitics | 戦争・制裁・資本規制・選挙 | 経路④（両義的：リスクオフ売り vs 検閲耐性買い） |

### 7.3 波及経路の定義（4経路）

| 経路 | 機序 | BTCへの符号 |
|---|---|---|
| ①実質金利経路 | 利下げ期待↑ → 実質金利↓ → 無利子資産の機会費用↓ | 実質金利低下＝強気 |
| ②ドル流動性経路 | 純流動性（Fed BS − RRP − TGA）↑ → リスク資産全般へ資金流入 | 流動性拡大＝強気（**歴史的にBTCと最も整合的な経路**） |
| ③リスク選好経路 | 景気・株式との相関（レジーム依存：相関は固定でない） | リスクオン＝強気（相関値は日次計測） |
| ④主権リスク経路 | 銀行危機・資本規制・通貨不安 → 「システム外資産」需要 | 条件つき強気（SVB型）。ただし急性リスクオフ時は当初売られる（COVID型）二段階反応 |

### 7.4 分析規律

1. **サプライズ駆動**：指標は実績値でなく `surprise = (実績 − コンセンサス) / 過去サプライズσ` で評価する。予想通りは原則ノーイベント。
2. **反応関数はレジーム依存**：「良い経済指標が売り材料になる」局面（利上げ懸念期）を扱うため、サプライズ→BTC反応の符号はレジーム別基準率で推定し、固定ルール化しない。
3. **二段階反応の明示**：地政学・銀行危機は「初動リスクオフ売り→物語形成後の買い」の二段階基準率を持つ（COVID・SVBのシードで検証済みのパターンとして登録）。
4. カレンダー駆動：経済指標・FOMC・満期日はwatch_pointsに事前登録し、発表後60分以内にイベント化（サプライズ幅・初動反応つき）。

## 8. Anomaly Engine

### 8.1 責務

カレンダー・周期性の統計的アノマリーを**検証済みの事前傾向（prior tilt）**として管理する。実行主体はScoring Agent（G11）内のルールベースモジュール（LLM不使用・全計算再現可能）。

### 8.2 アノマリーカタログ

| 分類 | 対象 | 検証する仮説の例 |
|---|---|---|
| 曜日 | 曜日別リターン・週末効果 | 週末の薄商い変動・月曜ギャップ |
| 月次 | 月別リターン（例：9月弱・10月強） | 「Uptober」等の通説の実証 |
| 四半期 | 四半期末のリバランス | 機関リバランスフロー |
| 半減期サイクル | 半減期からの経過月数別リターン分布 | サイクル位置の事前傾向（n=4に注意） |
| オプション満期 | 月次/四半期満期の前後リターン・ボラ | 満期前ピン→通過後方向解放 |
| 税金シーズン | 米4月・日本3月等の売り圧 | 納税資金化売り |
| 選挙・政治 | 米大統領選サイクル・主要国選挙 | 政策期待の織り込みパターン |
| ETFリバランス | 指数組入れ・四半期リバランス日 | 機械的フローの事前予測 |

### 8.3 統計的検証の規律（アノマリーの罠への防御）

アノマリーは**データスヌーピングの温床**である。以下を全カタログ項目に強制する：

1. **最低標本数**：n≥30（半減期等の構造的少数例は「統計」でなく「事例」として別扱い。n=4で「半減期後は上がる」を統計と呼ばない）。
2. **多重検定補正**：カタログ全仮説に対しBenjamini-Hochberg（FDR制御）を適用。補正後有意のみ「検証済み」ステータス。
3. **ロバスト性**：ブートストラップ信頼区間＋サブ期間安定性（前半/後半で符号一致）を要求。
4. **減衰監視**：検証済みアノマリーも公知化で消える。ローリング窓で効果量を監視し、有意性喪失で自動的に`decayed`ステータスへ降格。
5. **重みの上限**：アノマリーは単独シグナルとして絶対に使わない。総合スコアへの寄与上限を±5点にキャップ（§11.3）。他次元と合流したときのみ意味を持つ。

```jsonc
// アノマリー台帳レコード
{ "anomaly_id": "anm_options_expiry_pin", "category": "options_expiry",
  "hypothesis": "四半期満期前5営業日はMax Pain方向への回帰が有意",
  "status": "validated",          // candidate | validated | decayed | rejected
  "stats": { "n": 48, "effect_size": ..., "p_adj": 0.03, "subperiod_stable": true },
  "last_validated": "2026-06-30", "next_revalidation": "2026-09-30" }
```

## 9. Similarity Engine

### 9.1 責務

「現在の市場状況」および「個別の新規Event」を過去事例と比較し、**類似事例＋基準率＋今回との差分**を供給する。BIOSの独自価値の中核。実行主体はSimilarity Agent（G10）。

### 9.2 二つの比較モード

| モード | 問い | 出力 |
|---|---|---|
| **Event類似** | 「このイベントは過去の何に似ているか」 | historical_matches（news_analysis 7番に供給） |
| **State類似** | 「今の市場全体は過去のいつに似ているか」 | 類似日付リスト＋その後のリターン分布（Daily Reportの文脈欄に供給） |

### 9.3 市場状態ベクトル（State Vector）

State類似のために、毎日の市場を**6ブロックの特徴ベクトル**へ圧縮して保存する（全特徴はz-score化・point-in-time）：

| ブロック | 特徴例 |
|---|---|
| ニュース/イベント構造 | 直近30日のイベント種別分布（タクソノミ頻度ベクトル）・進行中Chain類型 |
| オンチェーン | MVRV/SOPR/Reserve/CDD等のz-score（§5） |
| マクロ | 実質金利・純流動性・DXY・株相関のz-score＋金融レジーム |
| 需給 | 需給バランス・Overhang Ratio・粘着需要比率（§3-4） |
| ボラティリティ | 実現ボラ・IV・ボラのボラ・レンジ日数 |
| デリバティブ | Funding/OI/Skew/Basisのz-score＋検知中パターン（§6.3） |

### 9.4 類似度の算出（3経路の重み合成）

```
similarity(A, B) =
    0.40 × 構造一致度   （Event類似：同taxonomy type＋Pattern台帳一致。State類似：イベント構造ブロックの一致）
  + 0.25 × 状態近接度   （State Vectorのブロック別コサイン類似の加重平均）
  + 0.20 × レジーム一致  （trend/vol/liquidity＋市場フェーズの一致度。不一致は強い減点）
  + 0.15 × 意味的類似   （記述埋め込みのコサイン。最も信頼度が低い経路として下限重み）
```

- 重みは`config/scoring.yaml`管理。**レジーム不一致（強気相場vs弱気相場）の事例は、他がどれだけ似ていても類似度上限0.6にキャップ**する（「強気相場のETF流出と弱気相場のETF流出は別物」原則）。
- 市場の構造断絶に対応するため、**時代区分（era）**を導入：pre-futures（〜2017）/ pre-ETF（2018〜2023）/ post-ETF（2024〜）。era跨ぎの事例は類似度に減衰係数を掛け、差分欄に「市場構造が異なる」を必須記載。

### 9.5 基準率（Base Rate）の算出規律

1. 類似事例集合（similarity ≥ 閾値）のN日後リターン分布（+1d/+7d/+30d/+90d：中央値・四分位・勝率・最悪値）を算出。
2. **n<5：統計を出力せず事例列挙のみ**（「統計的に語れない」を明示）。5≤n<15：分布は出すが`low_sample`警告必須。
3. **confounding警告**：各事例のリターンに併発イベントが混入している場合は警告を伝播。
4. 全事例に**類似点・相違点（必須）**を付す。相違点なしの「過去もこうだった」型出力は禁止（QA Agentの機械検査対象）。

## 10. Market Phase（市場フェーズ判定）

### 10.1 責務

Daily Reportの「市場フェーズ」と、全エンジンの文脈（Context段階）を供給する。レジーム（MSD §11）を拡張した**2層のフェーズモデル**。実行主体はScoring Agent（ルールベース主体＋LLMは説明文のみ）。

### 10.2 フェーズモデル

**第1層：Regime（機械判定・日次）** — trend（bull/bear/range）× vol（low/normal/high）× liquidity（easing/neutral/tightening）。判定はルール（移動平均構造・実現ボラpercentile・純流動性傾き）で全再現可能。

**第2層：Cycle Phase（サイクル位置・週次更新）** — オンチェーン世代分析を主入力とした4フェーズ：

| フェーズ | 定義（主なルール入力） | 典型シグナル |
|---|---|---|
| Accumulation（蓄積） | 価格Realized Price近傍・LTH供給増・Reserve減 | 底値圏・スマートマネー蓄積 |
| Markup（上昇） | 価格>RP・MVRV上昇途上・新規参入流入 | トレンド形成・押し目有効 |
| Distribution（分配） | 高MVRV＋CDD/Dormancyスパイク＋LTH供給減 | 古い手の出口・過熱 |
| Markdown（下落） | 価格<STH-RP・SOPR<1定着・降伏イベント | 損切り連鎖・悲観 |

- フェーズ判定は**確率ベクトル**（例：Markup 0.6 / Distribution 0.3 / その他 0.1）で持ち、断定しない。遷移はヒステリシス（確率0.5超がN日継続で確定）でチャタリングを防ぐ。
- フェーズはSimilarity Engineのレジーム一致・Scoring Engineの重みセット切替（§11.3）・Daily Report冒頭に使われる。

## 11. Scoring Engine

### 11.1 責務と設計思想

全DimensionReport（§1.3）を統合し、**「なぜその点数なのか」を完全に説明可能な総合スコア**を算出する。実行主体はScoring Agent（G11）。計算は**全てルールベース（LLM不使用）**とし、同じ入力から必ず同じスコアが出る（再現可能性・バックテスト可能性の前提）。

### 11.2 スコアの構造（3層の透明性）

```
Layer 1: Signal（最小単位）
  signal = { 観測値, z-score, 変換関数, points（寄与点）, evidence_refs }
Layer 2: Dimension Score（次元別 -100〜+100）
  dimension_score = Σ signal.points（次元内の署名つき合算・上限クリップ）
Layer 3: Composite Score（総合 -100〜+100）
  composite = Σ_d ( weight_d(phase) × dimension_score_d ) / Σ weight_d
```

すべてのDecisionは**Score Card**（3層全体のスナップショット）を保存する。任意のスコアから「どの次元の・どのシグナルの・どの観測値が・何点寄与したか」まで分解でき、観測値からevidence_refs経由でRawItemまで遡れる。

```jsonc
// Score Card（毎日保存・追記のみ）
{
  "score_card_id": "sc_2026-07-14_btc",
  "composite": -12,
  "verdict_hint": "NEUTRAL_BEARISH",     // スコア帯→語彙の機械変換（§12.4）
  "weights_version": "w_v14",           // 使用した重みセット（Git管理）
  "phase": { "regime": {...}, "cycle": {"markup": 0.55, "distribution": 0.35} },
  "dimensions": [
    { "dimension": "supply", "score": -35, "weight": 0.20, "contribution": -7.0,
      "top_signals": [ { "signal_id": "supply.overhang_ratio", "points": -20, "value": 3.2, "evidence_refs": [...] } ] },
    { "dimension": "derivatives", "score": +18, "weight": 0.25, "contribution": +4.5, "top_signals": [...] }
  ],
  "conflict_index": 0.62,               // §11.4
  "data_completeness": 0.94             // 欠損次元があれば減点でなく明示＋再正規化
}
```

### 11.3 重み付け（レジーム条件つき・ガバナンスつき）

- 重みセットは`config/scoring.yaml`で**市場フェーズ別**に定義する（例：Markup期はデリバ・フローの重み高、Accumulation期はオンチェーンの重み高。マクロショック期＝liquidity tightening時はマクロ重み自動増）。
- 初期重み（v1）は等重み起点＋定性調整とし、**以後の変更はバックテスト証拠＋ADRを必須**とする（§13.8のプロセス以外での重み変更は禁止）。
- アノマリー次元の寄与は±5点にハードキャップ（§8.3）。
- 欠損次元は0点扱いにせず**除外して再正規化**し、`data_completeness`として明示（欠損を中立と偽装しない）。

### 11.4 相反シグナルの扱い（Conflict Handling）

相反は平均化で隠さず、**第一級の情報として扱う**：

1. **Conflict Index** = 次元スコアの符号加重分散（0=全次元一致、1=真っ二つ）。
2. Conflict Index > 閾値のとき：(a) Decision Agentのconviction上限を自動的に引下げ（例：0.55まで）、(b) Daily Reportに「対立シグナル」セクションを強制表示（どの次元とどの次元が対立し、歴史的にどちらが先行したかの基準率を添付）、(c) デフォルト判断をWAIT側に倒す。
3. **時間軸の対立は対立ではない**：デリバ弱気（日次）×オンチェーン強気（週次）は「短期調整リスクを伴う中期強気」として時間軸別に分離表示する（スコアも短期/中期の2本立て：`composite_tactical`（〜7d）と`composite_strategic`（〜90d））。

### 11.5 スコア→判定の変換

| composite | verdict_hint |
|---|---|
| +40超 | STRONG_BULLISH |
| +15〜+40 | BULLISH |
| -15〜+15 | NEUTRAL（副語彙：NEUTRAL_BULLISH/NEUTRAL_BEARISH） |
| -40〜-15 | BEARISH |
| -40未満 | STRONG_BEARISH |

verdict_hintは**Decision（BUY/WAIT/TAKE_PROFIT）そのものではない**。Decisionはシナリオ確率・Critic反論・リスクポリシー・ポジション状態を加味してRisk Agent（G13）が確定する（スコアは判断材料の一つ）。

## 12. Daily Intelligence Report

### 12.1 生成方式

- 早朝バッチ（MSD §15.2）で**事前生成**し、「おはよう」で即時返却（5秒以内）。
- Report Agent（G14）は**新規分析をしない**。§2〜§11の成果物の編集・整形に徹する。数値は全てDB→テンプレート機械挿入（LLMに数値を書かせない）。
- 全掲載項目は成果物IDへの参照を持ち、「この行の根拠は？」に常に答えられる。

### 12.2 レポート構成（固定フォーマット・全17ブロック）

```
━━━ BIOS Morning Briefing ── 2026-07-14 06:00 JST ━━━
① 市場フェーズ     Regime（bull/high-vol/neutral）＋Cycle Phase確率＋前日からの変化
② 総合判定        WAIT（確信度0.6）← 昨日:WAIT ｜ 判定変化の理由1行
③ 総合スコア      -12（tactical -25 / strategic +8）＋次元別バー表示＋Conflict Index
④ 3行サマリ       今朝これだけ読めば分かる3行
⑤ 重要ニュースTOP10（briefing_priority順。各ニュース4行構造：
                    ├ Fact（何が起きた）
                    ├ Why/Trigger（なぜ・何がきっかけ）
                    ├ 市場の解釈（実反応データつき）

```

### 12.3 価格帯・利確・損切り・リスクリワードの算出規律

**価格レベルはLLMが「創作」してはならない。** 全レベルは以下の機械的候補から選定し、選定理由を明記する：

| レベル種別 | 機械的候補ソース |
|---|---|
| 推奨価格帯（押し目買いゾーン等） | Realized Price帯（LTH/STH別）・出来高プロファイル節・清算クラスタ・シナリオ基準率の四分位 |
| 利確候補 | 直近高値帯・シナリオ強気側の基準率P75・オプション大OIストライク |
| 損切り候補 | **無効化条件と必ず整合**させる（無効化＝損切りの価格表現）。STH-RP割れ・清算クラスタ下端等 |
| リスクリワード | (利確候補中央値 − 現在値) ÷ (現在値 − 損切り候補中央値)。1.5未満はBUY判断の障害として明示 |

- 全価格帯は**幅（ゾーン）**で提示し、点値を出さない。
- 憲法第7条により、これらは注文指示ではなく**分析上の参照レベル**である旨をレポート定型文で明示する。

### 12.4 深掘り対話（レポート後の質問）

| 質問類型 | 動作 |
|---|---|
| 「なぜ？」 | 該当ブロックのScore Card/分析の因果チェーンを展開（保存済み成果物の展開のみ） |
| 「FTXの時は？」 | Similarity Agentをオンデマンド起動し事例カードを返す |
| 「もし〜なら？」 | Scenario Agentを条件つき再実行（反事実分析・結果はJournalに記録） |
| 判断への反論 | 再考するが迎合禁止（変えるなら新根拠、変えないなら理由）。反論もJournalに記録 |

## 13. Backtest & Validation

### 13.1 目的

「BIOSの判断は本当に役に立っているか」を**毎日自動で記録し、+7d/+30d/+90dで自動検証**する。憲法第6条（計測なくして改善なし）の実行仕様。実行主体はRetrospective Agent（G17）＋Backtest実行系（ルールベース）。

### 13.2 検証の3系統

| 系統 | 問い | 方法 |
|---|---|---|
| **A. 判断検証（Decision Scoring）** | 個々のBUY/WAIT/TAKE_PROFITは正しかったか | Journal自動採点（§13.3） |
| **B. 確率検証（Calibration）** | 「70%」は70%起きているか | キャリブレーション曲線・Brier score（§13.5） |
| **C. シグナル検証（Signal Efficacy）** | どの指標・次元が効いているか | 指標別IC・寄与分析（§13.6） |

### 13.3 判断検証：仮想ポートフォリオ法

判断を採点可能にするため、**Decisionを仮想ポジションに機械変換**して追跡する：

- BUY → 仮想ロング1単位追加（上限あり）／ TAKE_PROFIT → 仮想ポジション解消 ／ WAIT → 現状維持。
- 執行価格はBriefing配信時刻（06:00 JST）のスナップショット値＋保守的スリッページ想定。
- この仮想ポートフォリオの日次リターン系列が指標計算（§13.4）の基礎となる。
- **WAITの採点**：WAITは「機会損失」と「回避損失」の両面で採点する（WAIT期間のリターンが+X%超なら機会損失、-X%超なら正解、区間内なら中立）。WAITを常に無得点にすると「何もしないAI」に退化するため、機会損失も明示的に減点する。

各Decisionレコードには+1d/+7d/+30d/+90dの結果を自動追記：

```jsonc
"outcome": {
  "+7d":  { "btc_return": +0.031, "verdict": "correct",  "scored_at": "..." },
  "+30d": { "btc_return": -0.052, "verdict": "incorrect", "scored_at": "..." },
  "+90d": { "pending": true },
  "invalidation_hit": false,          // 無効化条件が発動したか（発動＝設計通りの敗北として別分類）
  "confounding_note": "..."           // 判断後に発生した想定外イベント
}
```

### 13.4 評価指標（仮想ポートフォリオ基準）

| 指標 | 定義 | 目標水準（初期・改訂はADR） |
|---|---|---|
| 勝率（Win Rate） | verdict=correct の割合（ホライズン別・アクション別） | >52%（+7d） |
| 期待値（Expectancy） | 平均リターン×勝率 − 平均損失×敗率（1判断あたり） | 正値の維持 |
| Profit Factor | 総利益 ÷ 総損失 | >1.3 |
| Sharpe Ratio | 仮想PF日次リターンの年率化シャープ | > Buy&Holdシャープ |
| 最大ドローダウン | 仮想PFの最大下落率 | < Buy&HoldのMDD × 0.7 |
| **対ベンチマーク超過** | 仮想PF − Buy&Hold（BTC永続保有） | **最重要**。B&Hに勝てないなら判断機能に存在価値がない |

**ベンチマーク規律**：全指標はBuy&Hold・単純ルール（例：MA200上でロング）と並記する。絶対値でなく**超過**で評価する。

### 13.5 確率検証（Calibration）

- 全confidence/probability出力（news_analysis・scenario・decision conviction）をビン別（50-60%, 60-70%…）に集計し、**予測確率 vs 実現頻度**の較正曲線を月次生成。
- 指標：Brier Score・較正誤差（ECE）。恒常的過信（例：70%と言って55%しか当たらない）が検出されたら、Scenario Agentへ**縮小係数**（確率を基準率方向へシュリンク）を自動適用し、係数もJournalに記録。
- シナリオの**先行指標の的中**も検証：シナリオ採択時に掲げた先行指標が実際に点灯してからシナリオが実現したか（先行指標の質の検証）。

### 13.6 シグナル検証（指標別有効性）

- **IC（情報係数）**：各シグナル（§11 Layer 1）の値と先行リターン（+1d/+7d/+30d）のスピアマン順位相関をローリング計測。
- **次元別寄与分析**：Score Cardの履歴から「各次元の寄与と実際のリターンの整合」を分解。恒常的に逆相関の次元・シグナルは重み見直し候補として自動フラグ。
- **合流パターン検証**：§6.3等の公認パターンの発火後リターン分布を蓄積し、パターン台帳に実績を焼き付ける。
- 減衰監視：全シグナルICのローリング低下を検知（アノマリー§8.3と同じ仕組みを一般シグナルにも適用）。

### 13.7 Look-ahead Bias の構造的排除（バックテストの生命線）

1. **known_at原則**：バックテスト時、システムは日付Xの`known_at ≤ X`のEvent・取得時点のスナップショット値のみ参照できる（append-only設計の帰結。実装時はクエリレイヤで強制）。
2. **Point-in-time データ**：事後改訂される系列（オンチェーン帰属・経済指標改定値）は取得時点値を別保存し、バックテストは初報値を使う。
3. **LLM時間汚染への防御（最重要の落とし穴）**：LLMの学習データは過去の「結果」を含むため、**歴史期間のLLM分析を含むバックテストは原理的に汚染される**（モデルはFTXの結末を知っている）。対策：
   - ルールベース部分（Scoring・シグナル・アノマリー）のバックテストとLLM部分の検証を**分離**する。ルール部分のみ長期バックテスト可能。
   - LLM込みの端到端検証は**運用開始後のライブ実績（paper record）のみを真の検証**とする。「歴史データでLLM判断が当たった」ことを性能根拠にすることを禁止する。
   - ゴールデンテストは「正しい構造で分析できるか」（形式検証）に限定し、「当たるか」（性能検証）と峻別する。

### 13.8 改善ループのガバナンス（過学習への防御）

| 規律 | 内容 |
|---|---|
| 変更の最小単位 | 重み・閾値の変更は月1回まで・1回に1系統まで（何が効いたか識別可能に保つ） |
| ウォークフォワード | 重み変更はin-sample最適化→out-of-sample検証を通過したもののみ。全期間最適化は禁止 |
| 最低標本 | 判断数<60の状態での重み変更禁止（初期は観測に徹する） |
| 変更の記録 | 全変更はADR＋weights_version（Git）。Score Cardに使用バージョン刻印済みのため、新旧重みの成績比較が常に可能 |
| 多重検定 | シグナル追加候補の検定はFDR補正（§8.3と同一規律） |
| 検証レポート | 日次自動採点 → 週次サマリ → 月次キャリブレーション → 四半期重みレビュー（人間承認） |

## 14. Quant Research セルフレビュー

世界トップレベルのQuant Researchチームの視点で本設計を検査した結果。**反映済み**＝本書に組込済。**提案**＝オーナー承認待ち。

### 14.1 本設計の強み（自己評価）

- 説明可能性の徹底（Score Card 3層・証拠チェーン）は機関水準。「なぜこの点数か」に常に答えられる設計は個人向けシステムとして異例に強い。
- known_at原則・point-in-time・仮想ポートフォリオ・ベンチマーク超過主義は、バックテストの典型的な自己欺瞞（look-ahead・cherry-picking・絶対値評価）を構造的に塞いでいる。
- LLM時間汚染（§13.7-3）を明示的に扱う設計は、LLM系投資分析システムの大半が見落とす点である。

### 14.2 統計的に最も危険な弱点（率直な警告）

| # | 弱点 | 影響 | 手当 |
|---|---|---|---|
| W1 | **標本の少なさ**。日次判断は年間~250件、重要イベントは年間数十件。統計的有意性が出るまで1〜2年かかる | 初年度の「成績」はほぼノイズ | 反映済：最低標本規律（§13.8）。追加提案：初年度はKPIを「判断精度」でなく「構造化品質・キャリブレーション」に置く（当てることより測れることを先に完成させる） |
| W2 | **非定常性**。BTC市場は4年で構造が変わる（era設計§9.4）。過去の基準率の将来有効性は保証されない | 基準率への過信 | 反映済：era減衰・レジーム条件付け・減衰監視。原理的に消せない残余リスクとして憲法第5条（確率思考）で受容 |
| W3 | **半減期サイクル n=4 問題**。市場で最も語られる周期の標本が4 | サイクル論への過度の依存 | 反映済：構造的少数例は統計でなく「事例」扱い（§8.3） |
| W4 | **相関シグナルの共線性**。オンチェーン・需給・デリバの各指標は互いに強相関し、実効次元は見かけより少ない | 「多数のシグナルが一致」の過大評価 | **提案P1**：次元間相関行列の月次監視＋Conflict Index計算での相関調整（独立を仮定しない） |

### 14.3 不足していた機能・分析（追加提案）

| # | 提案 | 内容 | 優先度 |
|---|---|---|---|
| P1 | シグナル相関監視 | W4対応。次元間・シグナル間の相関行列を月次計測し、実効自由度をScore Cardに記載 | 高 |
| P2 | **Positioning / Sentiment次元の追加** | COT（CME建玉報告）・Fear&Greed・アプリストアランキング・検索トレンド。「誰がどっちに傾いているか」は§6のデリバだけでは機関偏重になる。第8の次元として追加 | 高 |
| P3 | **クロスアセット相関エンジン** | BTC-株・BTC-金・BTC-DXYのローリング相関とその**断絶検知**（correlation_break）。マクロ経路③の定量化に必須。マルチアセット拡張（MSD §16）の先行実装を兼ねる | 中 |
| P4 | 不確実性の区間表示 | 確率の点表示（45%）でなく区間（40-55%）。標本が少ない基準率ほど区間を広く（ベイズ縮小：事例が少ないほど無情報事前分布へ寄せる） | 中 |
| P5 | ナラティブ追跡 | 市場の支配的物語（「機関採用」「インフレヘッジ」等）の変遷をタグ化・追跡。反射性（物語が価格を作り価格が物語を強化する）の観測。LLMの得意領域 | 中 |
| P6 | データ品質エンジン | ソース別の欠損率・改訂頻度・遅延の常時計測。信頼度をSource reliability_scoreへ自動反映 | 中 |
| P7 | Backtest Agent（G18）の正式化 | §13の実行主体を専用Agent化（MSD §19.3で保留していたもの。本書で仕様が確定したため採用を推奨） | 高 |
| P8 | 週次Deep Dive Report | 日次と別に、週次で1テーマを深掘りする長文レポート（進行中Chainの総点検・キャリブレーション報告）。日次の速さと週次の深さの分業 | 低 |

### 14.4 追加すべき設計思想（本書に反映済み）

1. **「当てる」より「測る」が先** — 初年度の成功指標はリターンでなく、キャリブレーションと証拠チェーンの完全性（W1の帰結）。
2. **Buy&Holdに勝てないなら判断するな** — 全成績はB&H超過で評価（§13.4）。BTCの長期上昇局面では「常にBUY」が最強戦略になり得ることを直視する。
3. **LLMの記憶はバックテストの敵** — 歴史データでのLLM性能検証を性能根拠にしない（§13.7-3）。
4. **相反は情報である** — シグナル対立を平均化で隠さず、Conflict Indexとして第一級で扱う（§11.4）。
5. **アノマリーは香辛料** — 主菜（需給・フロー・マクロ）にはなれない。寄与上限のハードキャップ（§8.3）。
