## 1. 何を測るか（3階層）

| 階層 | 問い | 指標 |
|---|---|---|
| L1 データ品質 | 事実は正確か | 証拠なしFACT検出率 / 重複Event率 / Event見逃し率（後日発覚した重要イベントを拾えていたか）/ 収集欠損率 |
| L2 分析品質 | 確率は当たっているか | **Brierスコア** / キャリブレーション曲線 / シナリオ的中率 / 基準率適用の妥当性 |
| L3 判断品質 | 判断に従うと儲かったか | 判断追従仮想損益 / ベンチマーク比較（後述）/ 無効化条件の発動精度 |

## 2. Decision Journal の採点

すべてのDecisionは以下で事後採点する（Retrospective Agentが自動実行、月次でオーナーレビュー）。

```jsonc
{
  "decision_id": "dcs_2026-07-14",
  "scored_at": "2026-08-14",
  "horizons": {
    "+7d":  { "btc_return": 0.03, "action_pnl": 0.0 },   // WAITなら機会損益も記録
    "+30d": { "btc_return": 0.08, "action_pnl": 0.0 }
  },
  "scenario_outcome": "続伸",            // どのシナリオが実現したか
  "assigned_prob": 0.45,                 // 実現シナリオに事前に与えていた確率
  "brier_component": ...,
  "invalidation_triggered": false,
  "verdict": "process_good_outcome_missed",  // §3の4象限
  "lesson": "ETF流入の持続性を過小評価。基準率の母集団選択に偏り"
}
```

### 重要な規律：結果とプロセスを分離する

| | 良い結果 | 悪い結果 |
|---|---|---|
| **良いプロセス** | 理想 | **責めない**（正しい確率判断でも4割側は起きる） |
| **悪いプロセス** | **最も危険**（幸運を実力と誤認し悪癖が固定化） | 改善対象 |

採点は必ず「プロセス評価」（証拠は十分だったか、基準率は正しく使われたか、反対材料を見ていたか）と「結果評価」を別立てで行う。

## 3. キャリブレーション

- 四半期ごとに、確信度・シナリオ確率の**キャリブレーション曲線**を描く：「70%と言った事象は実際に何%起きたか」。
- 系統的過信（70%発言の実現率が55%）が検出されたら、Scenario Plannerのプロンプト・基準率ロジックを修正し、修正前後をゴールデンテストで比較。
- Brierスコアの移動平均を「BIOSの知能指数」として単一グラフで追跡する。**この線が下がり続けることがプロジェクト成功の定義**。

---

## 4. ベンチマーク（BIOSは何に勝てばよいか）

BIOSの判断追従仮想損益を、常に以下と比較する：

1. **Buy & Hold**（何も考えず持ち続ける）— 最強のライバル。BTCの長期上昇局面ではB&Hに勝つのは極めて難しいという事実から目を逸らさない
2. 単純ルール（例：200日移動平均上ならBUY）
3. コイン投げ（ランダム判断）

**BIOSの当面の勝利条件は「リターンでB&Hに勝つ」ではなく、(a)ドローダウン回避で優位、(b)確率のキャリブレーションが正確、(c)重大イベントの見逃しゼロ、に置く**（現実的かつ検証可能な目標設定）。

---

## 5. バックテスト（歴史リプレイ）

append-only設計と`known_at`フィールドの成果として、**「その日に知り得た情報だけ」で過去日の判断を再現**できる。

- 手順：日付Xを指定 → known_at ≤ X のEventのみでパイプラインを実行 → 生成された判断を実際のその後と照合。
- 用途：(a)プロンプト・ロジック改善の効果測定（同じ過去区間で新旧比較）、(b)新モデル移行の検証、(c)「FTX崩壊の前日、BIOSは何と言ったか」の検証。
- **look-ahead biasの三大侵入口**を常時監査：`known_at`の誤設定 / 後日訂正されたデータの遡及利用 / 埋め込みモデルが将来知識を含む問題（埋め込み検索はバックテストでは補助扱いにする）。

---

## 6. 見逃し検知（Recallの計測）

精度（言ったことが正しいか）だけでなく**再現率（起きたことを拾えたか）**を測る：

- 週次で「今週BTCが±3%以上動いた時間帯」を列挙し、その原因EventがStoreに存在するかを照合。存在しなければ「見逃し」として記録し、どのソースを追加すべきかをDATA_SOURCE_REGISTRY.mdの改訂候補に挙げる。
