# EVALUATION.md
# 予測精度の測り方

> 上位文書：`CONSTITUTION.md` 第7条「計測なくして改善なし」
>
> 予測AIの価値は「賢そうな文章」ではなく「予測が当たっているか」で決まる。
> それを測る仕組みがなければ、MIOSは5年後も初日と同じ精度のままである。
>
> **現状：実装済み（Phase 9）。** `src/mios/validation/` と `mios validate` / `mios accuracy`。
> 未実装なのはコンセンサス予想との比較のみ（取得元が未定のため。§3 参照）。

---

## 1. 何を測るか（3階層）

| 階層 | 問い | 指標 |
|---|---|---|
| L1 データ品質 | 数値は正確か | 出典なし観測値の検出数 / 欠損率 / vintage の取りこぼし / 発表を拾えなかった件数 |
| L2 予測品質 | 予測は当たっているか | **MAE / RMSE / 方向的中率 / 上振れ下振れ的中率 / キャリブレーション** |
| L3 有用性 | コンセンサスより良いか | 対コンセンサス相対誤差 / 対ナイーブ相対誤差 |

---

## 2. 採点の対象

実績には**最初に発表された値**を使う（最新の改定値ではない）。
予測者が当てようとしているのは「発表される数字」であり、
改定値で採点すると的が動いて、採点を走らせるたびに答えが変わってしまう。

```
predictions(target=US CPI YoY, period=2026-10, predicted_at=2026-09-12) = 3.3%
        ↓  実績発表（release_date=2026-11-13, actual=3.4%, consensus=3.2%）
forecast_errors:
    error            = +0.1pp      （actual − prediction）
    abs_error        =  0.1pp
    direction_hit    = true        （上振れを予測し、実際にコンセンサスを上回った）
    consensus_error  = +0.2pp      （actual − consensus）
    days_ahead       = 62
```

**予測は上書きしない。** 同じ対象に対する予測が毎日1行ずつ積み上がるので、
「発表10日前の予測」「発表1日前の予測」を分けて採点でき、
**予測の精度が発表に近づくにつれて改善しているか**を測れる。
これは単一の点予測では絶対に測れない性質である。

## 3. ベンチマーク（MIOSは何に勝てばよいか）

MIOSの予測誤差を、常に以下と比較する：

1. **ナイーブ予測**（直近3期の平均）— **実装済み。** 全予測に `baseline_value` として
   併記され、`skill = |baseline誤差| − |予測誤差|` が保存される。
   これが正でなければ、先行指標は飾りである
2. **機関予測** — 最強のライバル。**CPI については実装済み**（ADR-012）。
   Cleveland Fed の inflation nowcast を `external_forecasts` に vintage 付きで保存し、
   `external_forecast_errors` で **MIOS とまったく同じ条件**で採点する。
   市場が集合知で出した数字に個人のシステムが勝つのは極めて難しいという事実から目を逸らさない
3. **直近12ヶ月平均** — 未実装

### 3.1 「まったく同じ条件」の中身

比較が公平でなければ、出てくる数字は発見ではなく比較方法の副産物になる。
3つを揃える：

| 揃えるもの | 中身 | 揃えないと何が起きるか |
|---|---|---|
| actual | 対象期間の**初回発表値** | 改定値で採点すると、採点を実行した日によって同じ予測の点数が変わる |
| ナイーブ基準 | `changes_of` + `trailing_mean` を、**その予測自身の vintage 時点で再計算** | MIOS 側が保存していた baseline を流用すると、`skill` が両表で別の意味になる |
| 情報量 | MIOS の予測の as-of 時点で**知り得た**相手の最新予測だけを突き合わせる | 30日前の予測を発表当日の nowcast と比べることになり、どちらに転んでも別の問いの答えを並べただけになる |

3つ目が最も重要で、かつ最も静かに壊れる。
相手の予測を `published_at` で読むと、1年分をまとめて取得した日に
「ずっと前から知っていた」ことになってしまう。読み出しは常に `vintage_at`
（MIOS が実際に取得できた時刻）で絞る。統合テストがこれを直接検査している。

### 3.2 雇用統計はベンチマークできない

NFP と失業率の月次コンセンサスは有料（Bloomberg / Reuters のエコノミスト調査）であり、
中央銀行は「その月の発表値」の予測を公表していない。
SEP と SPF は失業率を扱うが四半期・Q4/Q4 の見通しであって、別の問いである。
別の問いの答えを流用して比較したことにするのは、数字を捏造するのと同じ種類の誤りである。

したがって **NFP と失業率については、比較対象はナイーブ基準しかない。**
この2つの skill は CPI の skill より弱い主張であり、
`config/external.yaml` の `uncovered` に明示列挙され、
`mios accuracy` と日次レポートが毎回名指しで表示する。

**当面の勝利条件は「コンセンサスに勝つ」ではない。**

- (a) 誤差が**測れている**こと（そもそもこれができていない状態から始まる）
- (b) 誤差が機関予測と同程度の桁に収まること（CPI については `mios accuracy` の
  head-to-head で直接読める。`edge` が正なら、同じ情報量の時点で MIOS の方が近かった）
- (c) 方向（上振れ / 下振れ）の的中率が 50% を有意に超えること
- (d) 重要指標の発表を取りこぼさないこと

に置く。現実的かつ検証可能な目標設定である。

## 4. キャリブレーション

MIOS は「上振れ確率 65%」のような確率も出す。確率を出す以上、測る義務がある。

- 四半期ごとにキャリブレーション曲線を描く：
  「上振れ65%と言った事象は、実際に何%上振れしたか」
- 系統的過信（65%発言の実現率が52%）が検出されたら、
  予測ロジックを修正し、修正前後を同一期間で比較する
- **Brier スコアの移動平均を「MIOSの知能指数」として単一グラフで追跡する。**
  この線が下がり続けることがプロジェクト成功の定義

**確率を出すなら基準率を持つこと。** 基準率のない確率は数字の形をした感想である
（BIOS はここで失敗した：確率が composite スコアの線形変換にすぎず、
キャリブレーションを測っても式の傾きしか分からなかった。監査 §15 V-4）。

## 5. 結果とプロセスを分離する

| | 良い結果 | 悪い結果 |
|---|---|---|
| **良いプロセス** | 理想 | **責めない**（正しい確率判断でも外れる側は起きる） |
| **悪いプロセス** | **最も危険**（幸運を実力と誤認し悪癖が固定化） | 改善対象 |

採点は必ず「プロセス評価」（入力データは揃っていたか、先行指標を正しく使ったか、
相反シグナルを見ていたか）と「結果評価」を別立てで行う。

## 6. バックテスト（歴史リプレイ）

vintage 設計と `as_of` 規律の成果として、
**「その日に知り得た情報だけ」で過去日の予測を再現**できる。

- 手順：日付 X を指定 → `vintage_at <= X` の観測値のみでパイプラインを実行 →
  生成された予測を実際の発表と照合
- 用途：(a) ロジック改善の効果測定（同じ過去区間で新旧比較）、
  (b) 「CPI発表の1週間前、MIOSは何と言ったか」の検証

**look-ahead bias の三大侵入口**を常時監査する：

1. `vintage_at` の誤設定（改定値を当時の値として使う）
2. `observation_date`（参照期間）と `release_date`（発表日）の取り違え
3. `as_of` フィルタを通さない読み出し経路の存在

3 については、`as_of` なしで `observations` を読むコードを静的検出するテストを
Phase 4 で追加する。規律を人間の注意力に任せない。

---

## 7. 見逃し検知（Recall の計測）

精度（言ったことが正しいか）だけでなく**再現率（起きたことを拾えたか）**を測る：

- 週次で「USDJPY または Gold が大きく動いた時間帯」を列挙し、
  その原因となる指標発表・政策イベント・ニュースが DB に存在するかを照合する
- 存在しなければ「見逃し」として記録し、
  どのソースを追加すべきかを `DATA_SOURCE_REGISTRY.md` の改訂候補に挙げる

## 8. 運用サイクル

| 頻度 | 活動 |
|---|---|
| 日次 | 欠損レポート / 収集失敗ソースの明示 |
| 発表ごと | `releases` 到着時に `predictions` と自動突合 → `forecast_errors` |
| 週次 | 見逃し検知 |
| 月次 | 予測誤差レビュー（オーナー30分） |
| 四半期 | キャリブレーション曲線 / ベンチマーク比較 / ソース棚卸し / バックアップ復元訓練 |
