# PROJECT_CONSTITUTION.md
# Bitcoin Intelligence Operating System（BIOS）憲法

> 本書はBIOSプロジェクトの最上位文書である。他のすべての設計書・実装・運用は本書に従属する。
> 本書と矛盾する実装・提案は、本書を改正しない限り無効である。

---

## 第1条：ミッション

毎朝「おはよう」の一言で、世界中のBitcoin市場で**何が起き、なぜ起き、市場がどう反応し、過去の類似事例と何が違い、今後どのシナリオが最も確からしいか**を事実ベースで構造化し、**「今日は買うべきか、待つべきか、利益確定すべきか」を根拠・確率・無効化条件つきで提示する**こと。

BIOSは「予想AI」ではない。**事実を構造化し、因果と統計で確率を推定する分析OS**である。

---

## 第2条：思想の中核 — 分析パイプライン

すべての分析は以下の順序を厳守する。順序の飛ばし・逆転は禁止。

```
Fact（事実）
  ↓ 何が起きたか。検証可能な一次情報のみ
Evidence（証拠）
  ↓ 出典・引用・データ。すべてのFactは証拠IDを持つ
Timeline（時間軸）
  ↓ いつ起きたか。前後関係の確定
Context（文脈）
  ↓ どういう状況下で起きたか（レジーム・マクロ環境）
Cause（因果）
  ↓ 何がトリガーで、何が背景か
Market Reaction（市場反応）
  ↓ 価格・出来高・デリバティブ・フローは実際にどう動いたか
Historical Comparison（歴史比較）
  ↓ 過去の類似事例・基準率（base rate）・今回との差分
Probability（確率）
  ↓ シナリオ別確率。点予想ではなく分布
Decision（判断）
  ↓ BUY / WAIT / TAKE_PROFIT ＋根拠＋無効化条件
```

**下流の工程は上流の工程の成果物のみを入力にできる。** DecisionがFactを飛ばして「雰囲気」から生成されることを構造的に不可能にする（→ AI_AGENT_SPECIFICATION.md）。

---

## 第3条：Event First — ニュースは保存しない

1. 保存対象は**Event（出来事）**である。ニュース記事はEventに添付される**Evidence**にすぎない。
2. 同じ出来事を報じる100本の記事は、1つのEventと100個のEvidenceになる。
3. Eventは**Event Chain（イベント連鎖）**に属することができる。
   例：`Mt.Gox破綻 → 裁判 → 返済延期 → ウォレット移動 → 返済開始 → 市場反応（+30日 / +90日）`
4. Eventは**追記のみ（append-only）**。過去のEventの改変は禁止し、訂正は「訂正Event」として追加する。これにより「あの時点で何を知っていたか」を常に再現できる（look-ahead bias の構造的排除）。

---

## 第4条：事実主義 — 憶測の禁止

1. **一次情報 ＞ 二次報道 ＞ 解説・意見** の優先順位を厳守する（→ DATA_SOURCE_REGISTRY.md のTier制度）。
2. すべての主張は次の3分類のいずれかのラベルを必ず持つ：
   - `FACT`：一次情報で検証済み（証拠ID必須）
   - `REPORTED`：報道されているが一次確認できていない（出典必須）
   - `INFERENCE`：システムによる推論（推論根拠の明示必須）
3. ラベルなしの主張は出力してはならない。証拠のない`FACT`は生成できない（スキーマで強制する）。
4. AIが知らないことは「不明」と答える。埋め合わせの創作（ハルシネーション）は最大の敵であり、検証エージェントが常時監査する。

---

## 第5条：確率思考と無効化条件

1. 断定予想（「上がる」「下がる」）は禁止。出力は常に**複数シナリオ＋確率＋根拠**。
2. すべての判断は**Invalidation（無効化条件）**を持たなければならない。
   例：「BUY判断。ただしETF流出が3日連続で$500M超なら本判断は無効」
   無効化条件のない判断は判断ではなく願望である。
3. 確率は歴史的基準率（base rate）を起点とし、今回固有の差分で調整する。基準率を無視した「今回は特別」論は原則禁止（採用する場合は特別である根拠を明示）。

---

## 第6条：計測なくして改善なし

1. すべてのDecisionは**Decision Journal**に記録し、事後に採点する（→ EVALUATION_AND_CALIBRATION.md）。
2. 確率のキャリブレーション（「70%と言ったことは実際に70%起きているか」）を定期計測する。
3. 採点されない判断機能はリリースしない。**精度を測れない機能は存在しないのと同じ**である。

---

## 第7条：人間が最終決定者である

1. BIOSは**意思決定支援システム**であり、自動売買システムではない。発注機能はPhase計画上の最終段階まで実装せず、実装時も人間の承認を必須とする（→ RISK_AND_GOVERNANCE.md）。
2. 資金を失わせる可能性のある提案には、必ずリスク・反対根拠・最悪シナリオを併記する。
3. BIOSの出力は投資助言ではなく、オーナー個人の分析ツールである。

---

## 第8条：5年間保守できる設計

1. **運用者は一人**である前提で設計する。一人で理解・修理・拡張できない技術は採用しない。
2. 依存は最小限に。「流行っているから」は採用理由にならない。採用理由は必ずADR（Architecture Decision Record）として記録する。
3. データは資産、コードは消耗品。**Event Store（データ）を何よりも守る**。コードは全部書き直せてもデータが無事なら再建できる。逆は不可能。
4. すべての外部データソースは**必ず死ぬ**（API廃止・仕様変更・値上げ）前提で、ソースを差し替え可能な抽象化層を置く。
5. LLMモデルは**必ず世代交代する**前提で、プロンプト・モデル選択を設定ファイルに外出しし、モデル交換をコード変更なしで可能にする。

## 第9条：スコープ（やること・やらないこと）

### やること
- Bitcoin価格に影響するあらゆるイベントの構造化：ニュース / オンチェーン / ETF / 企業保有 / 政府保有 / マイナー / 取引所 / デリバティブ / マクロ / アノマリー / 供給・需要ショック / ウォレット移動 / 裁判 / 規制 / 経済イベント
- 歴史的イベントデータベース（Mt.Gox, FTX, LUNA, 半減期, ETF承認, 政府売却, SVB, コロナショック, 利上げ/利下げ 等）の構築と継続拡充
- 毎朝のブリーフィング生成と判断提示

### やらないこと（Non-Goals）
- 高頻度取引（HFT）・裁定取引 — 時間軸は「日〜週〜月」
- アルトコイン全般の分析 — BTCへの影響がある場合のみ文脈として扱う
- 秒単位のリアルタイム速報 — 速さより正確さと構造化を優先
- 万人向けサービス化 — オーナー一人のためのシステム（将来の拡張余地は残すが最適化はしない）

## 付録：用語定義

| 用語 | 定義 |
|---|---|
| Event | 検証可能な一つの出来事。ニュースではない。開始時刻・種別・関与主体・証拠を持つ |
| Event Chain | 因果・時系列で連なるEventの列（例：Mt.Gox破綻〜返済完了） |
| Evidence | Eventを裏付ける一次情報・データ・記事。URL/取得日時/信頼Tierを持つ |
| Market Reaction | Event発生後の市場データスナップショット（+1h/+1d/+7d/+30d/+90d） |
| Regime | 市場の体制（強気/弱気/レンジ、金融緩和/引締め等）。歴史比較の前提条件 |
| Base Rate | 類似イベント群における結果の歴史的発生率 |
| Invalidation | その判断が誤りだったと認定する客観的条件 |
| Decision Journal | 全判断の記録と事後採点台帳 |
